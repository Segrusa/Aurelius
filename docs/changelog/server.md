# Server changelog

The background server (`aurelius-daemon` and `aurelius-ctl`), released as
`server-v<version>`. `scripts/release.ps1 -Product server` takes a release's
notes from its section here; they become the GitHub release text and appear
under "What's new" for the server in Settings → Server & PC.

The server and the desktop app are released separately. They work together
as long as their protocol major matches. Releases up to v0.6.0 were combined:
see [CHANGELOG.md](../../CHANGELOG.md).

## v0.9.5

Protocol 5, migrations 43 to 47. The database is backed up before migration 45.

- **Work sessions replace quick tasks** (feature `work_sessions`, migration 43): a conversation of kind `session` is one employee working in one project's folder, started by a board member without a ticket, optionally in its own worktree and branch. `work_session.list` lists them, sorted on the last thing that happened, with `unseen` for a finished answer you have not opened. A run never starts without its tools. The composer sends model, effort and mode per session.
- **The dispatcher chooses who takes a session** (feature `session_dispatch`, migration 44): a session can be left to the dispatcher, which chooses its employee as it chooses a ticket's owner; while it chooses, `work_sessions.dispatch` is `choosing`, and `nobody` leaves the choice to a board member.
- **Chatting with an employee is gone** (protocol stays 5: methods and wire types stay, migration 45). Two things go: a board member's own chat with an employee (`conversations.board_member_id`, `chat_tickets`, the bridge tool `tell_responsible`) and the Team chat (the General channel and one channel per project, kind `group`, the employees' threads `channel:<id>`, the bridge tools `read_group_chat` and `post_to_group_chat`). Migration 45 deletes their conversations, messages, runs, usage, mailbox items and activity rows (the daemon backs the database up first) and drops `chat_tickets`; an employee's main chat (the one that holds its settings), tickets and their discussions, tasks, project conversations and work sessions stay. The features `employee_chats` and `team_channels` are no longer advertised. `employee.chats` answers an empty list and `employee.open_chat` is refused with "Chatting with an employee is no longer available."; `group_chat.send`, `group_chat.get`, `channel.list`, `channel.search` and `discussion.audience` only work for a ticket's channel (without one: `not_found`, "The Team chat no longer exists: write in a ticket's discussion."). An old call of the removed bridge tools is refused with a text that names `post_to_discussion` and `read_discussion`. A ticket opening or closing no longer leaves a line in General, a new project gets no channel, and `hand_off` only works in a ticket's discussion. `create_ticket` is for management only again. A message that wakes an employee in a ticket's discussion reads `[Discussion · from …]`; `PLATFORM_RULES_VERSION` 3 starts new sessions. A vault key export, and a vault name that runs may no longer have, now notify every board member in their Inbox (reason `server_notice`, one `company.updated` event with `changed: ["server_notice"]`) instead of writing a line in the Team chat; without that notification the key is not exported.
- **Session history and titles** (features `session_history`, `title`, `ticket_made_title`, migrations 46 and 47): every work session gets an AI summary, and `work_session.history` lists sessions next to Done tickets (`work_session.retry_summary` tries a failed summary again). A session gets a generated title after its first answer, and so does a ticket started from New session.
- **Code tab** (feature `code_view`, ticket #77): `code.get` shows a project's worktrees and branches and why each stays, `code.fetch` fetches every remote (a failing remote no longer stops the next, the repository's own ssh and `skipFetchAll` are kept), and `code.merge`, `code.remove_worktree`, `code.delete_branch` and `code.prune_merged` manage them. A branch an employee works on now, or an open ticket's branch, is left alone; the reads never take git's optional lock, and git's error lines pass the vault redactor.
- **Files with a message** (feature `chat_files`): a message in a session or a ticket can carry files of any type, photos and folders.
- **Decisions, subagents and compaction** (features `run_decisions`, `subagent_steps`, `compaction_setting`): a board member's answer or plan decision travels as `MessageView.decision`; each call names the subagent behind it, so a subagent's steps can be listed; a host setting sets Claude Code's compaction threshold, and a compaction mid-turn shows as a live status.
- **Lost writes** (feature `command_applied`): `command.applied` tells whether a write with an idempotency key committed, so a client asks before it calls a write failed after a dropped connection. The daemon logs when and why a client connection ended.
- **Employees and delegation**: an employee can run in several threads at once, a ticket's owner goes on when its last delegated part ends, and a ticket whose main task waits for its delegated parts still counts as working.
- **Install and reliability**: `scripts/update-server.sh` and `scripts/update-server.ps1` update only the server; the Windows install checks its build dependencies and stops running programs reliably. A fresh start writes and flushes each blob through one handle, a restore waits for a folder something still holds open, and a dropped store waits for its writer (Windows).

## v0.9.3

Protocol 5.

- **One question, one post** (additive to protocol 5, no migration): `run_said_last_in` no longer counts `suggest_replies`, `ToolSearch` or `TodoWrite` as work after a post, so a run that asked its question with `post_to_discussion` does not get its sign-off posted as a second message. A board member's message in a ticket's discussion, by `ticket.post` or `group_chat.send`, removes their `mention` notifications of that ticket. `EmployeeChatView.preview?`: the start of the latest message, for a list of chats.
- **Links to Claude Design** (feature `design_links`, additive to protocol 5, migration 40): `ProjectSummary.styleguide_url` and `project.update { styleguide_url }`, `TicketView.design_url` and `ticket.update { design_url }`, only `https://claude.ai/artifact/<id>` or `https://claude.ai/code/artifact/<uuid>` (max 300 characters; an empty text clears). `ticket.updated` says `changed: ["design"]`. Setting a link needs the right to approve on a paired device, clearing it does not. A run whose project has a styleguide or whose ticket has a design, on a Claude login and not ReadOnly, gets Claude Code's `Artifact` tool (`--tools`, `--allowedTools`; `ArtifactComments` and `ArtifactData` stay off with `--disallowedTools`; not asked, not blocked by an employee's own list) and a short block with the links at the end of its system text; the links are in the session key, so another link starts another session. Otherwise that block is one sentence: it cannot be opened here, ask the board member. The bridge tool `update_ticket` takes `design_url`.
- **Workspaces** (feature `workspace_filters`, additive to protocol 5, no migration): the reads `notification.list`, `approval.list`, `scheduled_message.list` and `activity_log.list` take an optional `project_id`. It narrows to what belongs to that project: a notification through its ticket, conversation, task or run, an approval through its task or conversation, an activity row through its `ticket:`, `channel:` or `chat:` thread. Without it they answer as before. A server without the feature refuses the field on the reads that had no params, so clients only send it when the feature is there.
- **Tickets from a chat** (additive to protocol 5, no migration): any employee may now use `create_ticket` in a run of a board member's lasting chat with it (`ConversationKind::Employee`, thread `chat:<conversation>`), also when it is no manager; the server checks this in `ticket::agent::create`. Outside such a chat only management can, as before. The ticket is linked in `chat_tickets` as before, so the Review update comes back to that chat. The employee's access level and tool list still apply.
- **Employees no longer note ideas**: the bridge tool `add_idea` is gone from what employees are offered and from their prompt text, the tool list (`employee.tool_options`) and the start profiles. A stored tool list that names it stays valid and loses the name on its next save. Existing ideas, `idea.*` and `EmployeeTaskOp::AddIdea` stay.
- **Unused features removed** (protocol stays 5, no migration, no table dropped; the empty tables and columns stay): notes (`note.*`), shares (`share.*`, and `task.discuss` that ran on them), task variants (`task.variants`, `task.choose_variant`, `variants.*`, `probe_worktree`), task dependencies (`depends_on`), old artifacts (`artifact.*`), plugins (`plugin.*`, `employee_plugins`, `project_plugins`), heartbeats, app keys, API keys, agent functions and function calls, webhooks (`webhook_outbox`, the `task.*` delivery), terminal (`terminal.*`), `git.get_diff` and `git.get_status`. Their feature flags and permissions are gone (`notes`, `project_plugins`, `project_plugins_employees`, `terminal_multi`, `app_keys`, `task_variants`, `management_channel`, `webhooks`). `aurelius-mcp` only worked with app keys, so the crate, its Docker image, `aurelius-mcp.exe` in the server zip and the gateway routes `/v1/mcp`, `/v1/functions` and `/v1/calls` went with them. A parked session starts a new Claude session once after this update, because its session key no longer holds plugins and artifacts; the conversation is re-sent, so nothing is lost.
- **An activity log and the employee's mailbox** (R8, U6; features `activity_log` and `employee_queue`, additive to protocol 5, migration 39): table `activity_log`, one row per delivery, queue step and run step, without foreign keys and without message text or tool input, kept 90 days. New reads `activity_log.list {employee_id?, thread_key?, ticket_number?, run_id?, category?, before_seq?, limit?}` and `employee.queue {employee_id}`; a board member's private chat is not in what another reads. `EmployeeSummary.activity_state?` (`working`, `waiting`, `queued`, left out when `idle`, unknown values read as `unknown`) and `EmployeeSummary.settings?` (its own provider, model and effort, left out when it inherits them all).
- **Tools per employee and start profiles** (C2, C6, P6; features `employee_tools` and `employee_profiles`, additive to protocol 5, no migration: in `employees.config_json`): `EmployeeConfig.tool_policy` holds `tools` (the switchable tools it has; none: all of its level), `approval_tools` (what always asks first) and `mcp_servers` (of those enabled server-wide). On `employee.create`, `employee.update` and `EmployeeSummary`; an update with it needs Approve on a remote connection. A tool that is off is left out of `--tools` or, for the bridge, not offered (`--without`); what asks first leaves `--allowedTools`, gets a `permissions.ask` rule for a built-in tool, and goes to the inbox in every mode, before any auto-allow, mode or 'Always allow'. `MEMORY_TOOLS` stays the list of bridge tools allowed by rule, minus what the policy takes out; every call of a tool that is off is denied in `permissions::ask`. A tool list is in the session key, only when there is one, so other employees keep their sessions. New reads `employee.tool_options` and `employee.start_profiles`; `employee.create` takes `start_profile`, and what the command leaves out comes from the catalogue in `crates/storage/seed/employees/`, a copy made once.
- **Scheduled messages and a scratchpad** (R7, C7, U3, U7; features `scheduled_messages` and `employee_scratchpad`, additive to protocol 5, migration 38): the bridge tools `schedule_message(delay, content, to?)` and `scratchpad(content)` (`EmployeeTaskOp`). A scheduled message keeps the login of the run that planned it, with no fallback; the dispatcher delivers what is due through the mailbox as one hop, and what cannot be delivered ends as `not_delivered` with a reason and a limit line. New reads `scheduled_message.list`, `thread.waiting {ticket_id?, conversation_id?}` and `employee.scratchpad {employee_id}`, new command `scheduled_message.cancel {message_id}`, `RunBrief.employee_id?`. Changes go out on the existing `recurring_task.changed` event with aggregate type `scheduled_message`.
- **Lasting chats with an employee** (feature `employee_chats`, additive to protocol 5, migration 37): `employee.open_chat {employee_id}` opens the acting board member's chat with an employee, made the first time (`conversations.board_member_id`, unique per employee and board member; `employee_conversations` and `is_older_employee_chat` skip these, and the main chat stays the oldest). `employee.chats` lists the reader's chats with messages, latest first, with unread. `chat.send` and `chat.retry` accept such a chat from its board member only, not for a paused or archived employee, and refuse older employee chats; a run goes through the mailbox with thread key `chat:<conversation>` on that board member's login, and `conversation.get` answers `not_found` to others. A ticket made by a run in the chat is linked by the server (`chat_tickets`); each arrival in Review counts in the transaction of the move, and a dispatcher pass writes one hidden `ticket_update` per chat for what waits, marks it told in the same transaction and queues one run. `ticket_update` is filtered out of `conversation.get`. New bridge tool `tell_responsible(message)` writes a `ticket_note` with a link to the ticket in the chat of the responsible board member: unread, no run, no notification.
- **Handoffs and hops** (R4, R5, additive to protocol 5): `@Name` in what an employee writes only refers to someone. The bridge tool `hand_off(to, message)` (`EmployeeTaskOp::HandOff`, in a ticket's discussion or a channel) posts "X handed over to Y" with the message in the thread (`meta_json.handoff_to`) and writes the inbox item at its hop. Every employee message has a hop in `meta_json` (a run's hop plus one; 0 for a board member, whose message resets it, also when it wakes someone else); delegations carry theirs on the task's job payload, and a result coming back counts none. `group_chat::hop_limit`: 3 in a channel, 8 on a ticket (assumption 1), also for `delegate_task`. A handoff while the sender has queued items in the thread is held (`employee_inbox.state = 'held'`, with a `limit` line carrying `action: handoff_held`) and delivered unchanged by `release_handoffs` once the sender has none and no run there. `PLATFORM_RULES_VERSION` 2.
- **Run cards and the odometer** (feature `run_cards`, additive to protocol 5, migration 35 `usage_records.model_calls`): a post of an employee in a discussion now has `MessageView.run_id` (read from its `meta_json`), and a run's `Reported` line finds its run through its task. Only the last post or line of a run in a list carries `MessageView.run` (`RunBrief`: status as a string, tool calls, failed calls) and `usage`. `MessageView.awaiting_user` (left out when false): the run has an open approval or question, or the post ended a ticket's main task on a question (`group_chat::asks_question`, the rule of `ends_on_question`). `ApprovalView.ticket_id` and `discussion_id` say where an approval is talked about. `run.get_activity {run_id}` lists a run's tool calls (previews, like `conversation.get`; Read on a remote connection, not for apps). `usage.get_totals` takes `ticket_id` (a ticket's tasks and the runs of its discussion) and a channel's `conversation_id` now counts the runs it woke; `TokenUsage.model_calls` counts model calls (0: not known, older records); `UsageSnapshot.by_user` is the usage of the last 30 days per Claude login.
- **Employees as bots, the prompt rules** (additive to protocol 5, no feature flag): every employee run starts with a platform block: hand off with the `hand_off` tool when someone else should act next (changed with the handoffs below), who leads a thread (on a ticket its responsible board member, else its owner; in a channel the project's dispatcher or the CEO), self-contained handoffs, `(new)` on the messages that woke the run (and `(new, arrived before your last reply; it may already be handled)` on one that came in meanwhile), a signature on external systems. The block has a version in the session key, so a new version starts new sessions (guidelines B6); the first run after this update starts one. An employee that is no lead and not alone in a thread gets only the messages addressed to it and its own in its prompt, with how many others there are and `read_discussion` / `read_group_chat` to read them; the clients keep showing the whole thread. New `description` on `employee.create`, `employee.update` and `EmployeeSummary` (at most 160 characters, migration 33): what the colleagues' list shows, as `- @Name (role): description`, else the first line of the instructions.
- **Memory scope rule**: the extraction prompt and the `remember` tool say that a fact that only holds for one ticket or task belongs in its discussion, not in memory (`aurelius-extract-3`).
- **`delegate_task` always lands on a ticket.** Inside a ticket's task or discussion it is that ticket. Elsewhere (a chat, a project conversation, a heartbeat, a task without a ticket) the employee names one with `ticket` (`#12`): the task gets the ticket's project, a line in its discussion, and comes back in the conversation. Without a ticket, or with one that is Done, in another project or on another board member's login, the tool refuses and says why. An escalation stays on the ticket of the task it comes from. Recurring tasks, functions and `task.create` for apps do not change.
- **An idea becomes a ticket.** `ticket.create { from_idea }` (feature `ticket_from_idea`) makes the ticket in one transaction with the idea's status: the idea is done, `IdeaView::ticket_id` and `ticket_number` point at the ticket, and the ticket has its own copies of the idea's files. Migration 31 adds `ideas.ticket_id`. `task.create` and `idea.start` stay for apps and older clients.
- **The mode of a group chat answer** (additive to protocol 3.0): an employee's answer in the group chat carries the mode its run started in, as `MessageView.mode` (stored in the message's `meta_json`) and, while it streams there, `StreamDelta.mode` / `StreamAppend.mode`. Left out for other messages and streams and by older servers.
- **Memory in Plan mode**: the plan-mode guidance now says that Aurelius' own memory tools (`remember`, `recall`, `add_idea`) work in Plan; files, commands and external actions stay refused. The bridge already allowed them in every mode, but the old text ("actions are refused") made employees skip them.
- **Group chat ("Team chat")** (additive to protocol 3.0): one conversation of the user with every employee, kind `group` (migration 17 rebuilds `conversations` with the new kind, copies every row and makes the group chat itself). Read `group_chat.get` (a `MessagesSnapshot`, Read right), write `group_chat.send {text, images, files}` (command `send_group_message`, Chat right; result `group_message_sent {conversation_id, message_id, to, run_ids}`). Apps cannot use either. The user's messages are user messages; an employee's are updates (`update: "group"`) with its name as `author`. `@Name` (any case) wakes those employees, without a name the CEO answers. Each answers in a normal run of its own main chat (the message arrives there as a `[Group chat · from …]` update with the latest 20 group messages); the answer is copied to the group when the run ends and streams there live (`StreamDelta.conversation_id` = the group, `message_id` = the id the answer gets there). New bridge tools `read_group_chat` (allowed in task trials) and `post_to_group_chat`: a post wakes only the colleagues it names, never the poster, at most 3 hops after one message of the user, at most 2 times per run and 4 times per employee per hour (a task's run starts again at hop 1, so the hourly cap is what stops a loop through tasks); later posts are shown but wake nobody. The group messages an employee gets (and `read_group_chat`) are a JSON list, and a colleague's message is JSON-quoted, so no post can pass for the user's; only the `[Group chat · from Owner]` label is the user. When a message of the user wakes nobody (the CEO or the named employees are paused, or there is no CEO), an update of kind `status` from Aurelius in the group says so. A copied answer of a run that failed or was interrupted ends with "(interrupted)" / "(interrupted: code)"; a woken run stopped before it started posts "(Could not answer: cancelled.)". The CEO's answers to the group chat are never sent to apps as `manager.replied`. The group chat cannot be deleted and takes no `chat.send`. `employee.chat` stays.
- **Finished tasks with a follow-up run** (additive to protocol 3.0, no feature flag): `TaskView.live_run` (`"running"` | `"queued"`, left out when none and for tasks that are not finished) is set on a succeeded, failed or cancelled task while a run in its conversation goes or waits to start, after someone wrote to it. The status does not change (the task is not reopened), so clients show it as working/queued instead of done. New event `task.run_changed` (aggregate: the task, no status change) when such a run is queued, starts or ends, so clients read the task again. Older servers leave the field out.
- **Management chooses its own task mode** (feature `management_chooses_mode`, additive to protocol 3.0): the CEO and their direct reports get a bridge tool `set_mode {mode: auto|plan, reason}` in a task the user gave no mode. Such a task starts in Plan; the choice shows in the thread as a task update of kind `mode_chosen` ("<name> chose Auto: <reason>") and in the audit log as the event `task.mode_chosen` (payload `employee_id`, `mode`, `reason`, `conversation_id`, `run_id`). `set_mode` is refused outside management, outside the task's own conversation, for modes other than Plan/Auto, while a plan waits for approval, and with the setting off. A delegation or hand-over to management no longer passes a mode on. Server setting: read `management_mode.get_setting`, write `management_mode.set_enabled {enabled}` (Approve right), both `ManagementModeSetting {enabled}`, on by default.
- **Management channel and webhooks for app keys** (features `management_channel` and `webhooks`, additive to protocol 3.0): an app key has an `audience` (`all`, the default and what every existing key is, or `management`). The server confines a `management` key to the CEO and the CEO's direct reports: `employee.list` and `task.list` show only them, tasks and messages for anyone else are refused, and the project assistant is out of reach. New MCP tools `ask_management`, `list_open_questions` and `answer_question`. A key can have a `webhook_url` (`http`/`https`) and gets a `whsec_…` secret once at `app_key.create`; Aurelius posts `manager.replied`, `question.for_you`, `task.finished` and `task.waiting` signed with HMAC-SHA256 (`X-Aurelius-Signature`), from a persistent outbox with retries and backoff and a stable delivery id. Migration 16. Contract: [aurelius-mcp.md](../aurelius-mcp.md).
- **The plain chat is gone**: every conversation belongs to a project, a task or an employee. Removed `conversation.list`, `conversation.set_web_research` (web research), `MessagesSnapshot.web_research`, the Chat run defaults (`Purpose` `chat`) and the ctl `chat`/`conversations` commands. `chat.send` and `attachment.add` need a conversation (project conversations); `task.discuss` gives the task's result to its lead employee's chat and returns `{ conversation_id, employee_id }`. Migration 15 deletes existing plain chats (after the pre-update backup) and rebuilds `conversations` without `chat` and `web_research`. Client list: [no-plain-chat.md](../v0.9.0/no-plain-chat.md).
- **Manual folder grants are gone**: removed `folder.grant` and `folder.revoke` (commands `grant_folder`, `revoke_grant`) and `ConnectionsSnapshot.grants`. They were never used. The work folders of projects and employees are untouched: they stay stored in `file_grants` and work as before, and the check for sensitive roots (drive roots, home, credential folders) still applies to them. Newer clients no longer call these methods; older clients show an empty Folders page.
- **A stopped run names what Claude Code loaded**: "Claude Code unexpectedly loaded tools (…) or MCP servers (…)" now lists the tool and server names instead of their number, and the daemon log has them as a warning, so a tool a new Claude Code version adds can be found and allowed. The run is still stopped.
- **`aurelius-mcp` ships with the release**: `aurelius-mcp.exe` is in the server zip (not replaced by updates), and the Docker image is published as `ghcr.io/segrusa/aurelius-mcp:<version>` and `:latest`.

## Unreleased

Fixes for apps that hung while opening a big task. Protocol 2.0, additive only (feature `activity_preview`); contract in [activity-preview-clients.md](../activity-preview-clients.md).

- **No more silent hang on a big reply**: over local IPC a reply over the 4 MiB frame limit is now answered with a `frame_too_large` error for its request and logged, instead of stopping the connection's writer without a word. Too large pushes are logged and dropped.
- **Short tool output** (feature `activity_preview`): `conversation.get` and live updates send each tool call shortened (output 2 KB, input strings 1 KB, with `truncated` and `output_bytes`); `activity.get` returns one call whole. A client that sends `accepts: ["activity_changes"]` in its hello gets only new or changed calls in live updates. The 575-call task that hung went from 5.0 MB to 1.2 MB.
- **Faster reads**: four read connections instead of one shared, and small blobs are kept in memory, so `memory.list` with thousands of items no longer opens a file per item on every reload (2,162 items: 0.27 s with warm files, 12.8 s cold, 66 ms from the cache).
- **Automatic session compaction** (feature `session_compaction`): a resumed conversation or task whose Claude Code session is above the settings key `session_compact_threshold` (default 120,000 tokens, 0 = off) is sent `/compact` before its next turn, with a full rebuild as fallback, and shows a "Context compacted" line in its timeline. Migration 13.

## v0.8.0

App keys for external apps and agents, and attachments on ideas. Protocol 2.0, additive only: works with the 0.7.x apps; the new parts need the 0.8.0 apps, which find them in `HelloResult.features` (`app_keys`, `idea_attachments`).

- **App keys and `aurelius-mcp`** (feature `app_keys`): external apps reach Aurelius through the separate `aurelius-mcp` binary (stdio, or `--http` at :7464/mcp, also as a Docker image). Each app has its own key with scopes read/draft/run/approve, hourly and concurrent limits and instant revoke; only owners manage keys. Without approve a task never runs in Auto, and tasks show which app created them.
- **Idea attachments** (feature `idea_attachments`): ideas carry files and images like tasks do (same ids, fetch and 25 MB cap). Starting an idea copies its files into the task, and `idea.delete` removes the idea with its files. Migration 7.

## v0.7.4

Project-wide plugins, editable project descriptions and a fix for stopping a run that waits for the quota. Protocol 2.0, additive only: works with the 0.7.x apps; the new parts need the 0.7.4 apps, which find them in `HelloResult.features` (`project_plugins_managers`, `project_description`).

- **Project descriptions** (feature `project_description`): `project.set_description` (`SetProjectDescription { project_id, description }`, with `expected_version` like a rename) sets or clears a project's description: trimmed, an empty text clears it, at most 2000 characters. The project's version goes up. No migration.
- **Stopping a parked run**: stopping a run or cancelling a task that waits for the quota reset now cancels its waiting job at once and marks the message interrupted, instead of leaving the run pending until the reset.
- **Project plugins for every manager** (feature `project_plugins_managers`): a project's plugin list is project-wide; every manager run in the project (tasks and conversations, every mode) loads the project's plugins plus the manager's own extras, without doubles. `ManagerPlugins` gets `inherited` (the project's ids, additive). The project assistant keeps loading the project's list.

## v0.7.3

Project notes, plugins per project, artifact snapshots, several terminals per conversation, Playwright as a browser backend and clearer waits. Protocol 2.0, additive only: works with the 0.7.x apps; the new parts need the 0.7.3 apps, which find them in `HelloResult.features` (`upload_fetch`, `notes`, `project_plugins`, `terminal.multi`).

- **Project notes** (feature `notes`): `note.list` (pinned first, search), `note.get`, `note.create`, `note.update` (with `base_revision`, a version conflict when it changed elsewhere), `note.set_pinned`, `note.delete`; events `note.created/updated/deleted`. Migration 4.
- **Plugins per project** (feature `project_plugins`): `plugin.get_for_project` / `plugin.set_for_project` and `PluginInfo::projects`; the project assistant loads its project's plugins, and a slash command (a plugin's or Claude Code's own) goes in as the prompt itself. Migration 5.
- **Artifact snapshots**: the published file of every artifact version is kept (`artifact.get_content`, migration 3), so the apps can show it inside Aurelius; artifacts of deleted conversations leave `artifact.list`.
- **Uploaded files** (feature `upload_fetch`): uploads get an id (`MessageFileView::id`) and `upload.get` fetches them whole or as a thumbnail.
- **Several terminals per conversation** (feature `terminal.multi`): `terminal.open` with `terminal_id` / `additional`, `terminal.detach` (the shell runs on) and `terminal.list`; at most 4 per conversation and 8 per server.
- **Playwright MCP** as a second browser backend next to Claude in Chrome. Claude in Chrome keeps one tab group per manager across runs.
- **Usage limit**: a task waiting for the limit shows its reset time (`TaskView.waiting_until_ms`, `JobSummary.not_before_ms` / `reason`), the run resumes its own Claude Code session afterwards, and kept sessions whose run will not resume are swept.
- **Queued tasks say why they wait**: `waiting_reason` `in_line` or `scheduled` with `starts_at_ms`, so apps count them as waiting, not active.

- **Fewer subagents in tasks.** A manager working on a task is told to do the work with its own tools and use subagents only for broad searches across many files.
- **Tasks one at a time** (protocol 1.8). A manager's worker policy has `sequential_tasks` (off by default), set with `update_manager` (`sequential_tasks`, left as it is when absent) and shown in `ManagerSummary.sequential_tasks`. When on, the manager works on one task at a time: its other tasks (new, delegated, handed over, repeating) stay queued (`task.queued` with reason `sequential`) and start in the order they were created. The turn passes on when the running task ends or waits (for the user or for colleagues) or goes to review. Turning it off starts the queued tasks; turning it on leaves tasks that already run alone. Conversations with the manager are not affected.
- **Delegated results answered together.** When a manager gave several tasks from one conversation, it answers once, when the last of them ended (or was cancelled), instead of once per result. A result that comes in while the conversation is answering is picked up when that answer ends.
- **Start an idea in a chosen mode** (protocol 1.8). `start_idea` takes an optional `run` (as `create_task`), so the idea's task conversation starts in that mode. Starting a task or idea in Auto needs the right to approve, as switching a conversation to Auto does.
- **A phone can set a manager's model even with a global persona or connection.** Setting a manager's model and effort from a phone now compares the connection and persona with the manager's own setting instead of the global one.

## v0.6.3

Restart the server from a client, send files to managers, and runs wait while the machine is busy (protocol 1.7).

- **Restart the server from a client** (protocol 1.7). The new method `server/restart` answers first and then stops the service, which starts itself again, as after an update. Any paired device that may approve can ask for it; `aurelius-ctl restart` does it from the command line. Answers that were running stop and show as interrupted, as with an update.
- **New answers wait while the machine is busy.** The server measures the computer's CPU and free memory (averaged over about 10 seconds) and starts a new answer or task only below 75 % CPU (again below 65 %) with more than 2 GB free, and at most 3 at a time; with nothing running, one always starts, and running answers are never stopped. Waiting answers stay queued and their run records why (`run.waiting`, reason `load:cpu`, `load:memory` or `load:max_runs`). `AURELIUS_MAX_RUNS`, `AURELIUS_CPU_HIGH`, `AURELIUS_CPU_LOW`, `AURELIUS_MIN_FREE_MB` and `AURELIUS_LOAD_ADMISSION=on|off` change this. Claude Code's builds use half the cores (`CARGO_BUILD_JOBS`).
- **Delegated work keeps the mode it was given in.** When a manager gives work to a colleague (delegate_task, from a task or a plain conversation, or hand_over_task), the colleague's task conversation starts in the giver's current mode if that is Auto or Accept edits, also further down a chain. Plan and Ask are not passed on; the conversation then starts as usual. The user can still change the mode afterwards.
- **Files with a message to a manager** (protocol 1.7). `send_manager_message` takes `files`: up to 8 files of any type, 25 MB each, as paths on the server or (from the phone) files in its own upload inbox. The server copies them into `.aurelius/uploads/` of the conversation's work folder (the project folder, else the manager's folder), which Git ignores, and tells the manager where they are. The message shows them as `uploads` (name, path, size). Without a work folder the message is refused with "no work folder".
- **Usage per hour** (protocol 1.7). The new query `query/usage_hours` returns the 24 hours of a server-local day with runs, tokens and cost per hour, with the same rights as `query/usage`.
- **A task's own change** (protocol 1.7). The new query `query/task_diff` returns the change of a task with a workspace of its own: its branch against the commit it started from (plus what is not committed yet while its worktree exists), or, for a separate folder without Git, its files as new files. Same shape and 512 KB limit as `query/git_diff`; nothing when the task has no workspace.
- **Who wrote an idea.** Ideas carry the id of the manager who noted them (`manager_id`, optional, so older apps keep working); an idea of a manager that has since been removed shows "A removed manager" instead of "You".
- **A task whose answer cannot start no longer stays running.** When the run of a task cannot be started after its retries, the task now waits for the user (reason `not_started`); sending a message in the task conversation lets it finish.
- **Standalone chats get no Git status, diff or terminal.** Only manager and task conversations work in a project folder; a plain chat gets no Git status or diff and is refused a terminal.

## v0.6.2

Managers keep answering, however much they remember.

- **Long instructions no longer stop a manager.** The system text (role, colleagues, tasks and memory) now goes to Claude Code as a temporary file instead of on the command line. On Windows a long text made every run fail with "The filename or extension is too long" (os error 206), and the manager stopped answering without saying why.
- **An answer that cannot start says why.** When a run cannot be started after its retries, the answer in the conversation now gives the reason instead of staying empty.
- **A fixed budget for memory.** At most about 4 000 tokens of memory go into a manager's instructions. Pinned memories always go in; other decisions go in most relevant first, and a long memory is cut there. Everything stays reachable with `recall`.
- **Memory consolidation.** Once a project's or a manager's memory holds 30 or more memories that may be merged (or about 3 000 tokens), a background job merges them into short points, at most once a day. Memories you wrote, accepted or pinned are left alone. A point may only name memories that exist; what it replaces is superseded and stays in History. A cut that looks too drastic becomes proposals for you instead. The new command `consolidate_memory` (protocol 1.6) starts it at once.

Every conversation knows its own subagents (protocol 1.6).

- **`query/subagents`.** Returns the subagents running in the answers of one conversation: a plain chat, a manager conversation or a task conversation. Older apps keep working; the manager overview is unchanged.

A manager can give work to a colleague, also outside a task.

- **Delegate from a conversation.** In a normal conversation with the user, a
  manager can decide to let a colleague do something (`delegate_task`). The
  colleague gets it as a task of their own, shown as "Delegated by …". The
  result comes back in the conversation that asked, and the manager answers
  on it. Before this the tool was offered there but always refused. A manager
  whose worker policy forbids delegating still does the work itself.
- **No lost results.** A colleague who finishes while the delegating manager
  is still answering no longer gets skipped. The manager goes on once more
  with the result before it writes the report.
- **Hand-over no longer stalls.** A task handed over while the old manager's
  answer was still running now starts with the new manager once that answer
  ends.

## v0.6.1

A new chat starts with the settings chosen before its first message.

- **Settings before the first message.** A new chat can be sent with its mode,
  browser and screen already set (next to web research), so the first answer
  runs with them. The phone uses this for its switches above the composer.
  Starting in Auto or with the browser or screen on needs the Approve right,

## v0.6.0

The first separate server release, built from the same code as the combined
v0.6.0.

- **Own releases.** The server has its own version and updates on its own in
  Settings → App & updates. A server update restarts only the server; open apps
  reconnect by themselves. A server-only install never receives the app.
- **Built-in terminal.** A manager conversation can open a shell in its work
  folder on this computer (owner rights only).
- **Subagents.** The server reports which subagents run and what they are
  doing; subagents run in the foreground, so answers no longer stall.
- **Diff and branch.** New queries for the branch, changed lines and full diff
  of a conversation's work folder.
- Managers see their project's tasks and their own earlier conversations; mode
  switches and Send now reach a running answer; stopping an answer ends the
  programs it started and withdraws its open approvals.
